# 백테스트 실행 런북

목적은 하나다. **"내 매매법의 기대값이 몇 R인가"** 를 숫자로 얻는 것.
그 숫자가 나오기 전까지 체크리스트 점수는 근거 없는 숫자다.

---

## 0. 실행 경로 고르기

| 경로 | 설치 | 시간 | 끊김 | 추천 상황 |
|---|---|---|---|---|
| **A. GitHub Actions** | 없음 | 미장 30분~1시간 | 거의 없음 (6시간 한도) | 기본. 결과가 자동 커밋된다 |
| **B. Google Colab** | 없음 | 위와 비슷 | 90분 무활동 시 끊김 | Actions 를 못 쓸 때 |
| **C. 로컬 PC** | Python 필요 | 가장 빠름 | 없음 | 반복 실행·규칙 튜닝 |

세 경로 모두 **같은 스크립트**(`backtest/run.py`)를 돌린다. 결과는 동일하다.

## A. GitHub Actions

1. https://github.com/milianjw8-hue/jwcha-stock/actions/workflows/backtest.yml
2. **Run workflow** 클릭
3. 입력:

   | 항목 | 값 |
   |---|---|
   | Use workflow from | **`main`** |
   | 시장 | `us` (처음엔 한쪽만) |
   | start | `2019-01-01` |
   | split | `2024-01-01` |
   | universe | `150` |

4. 실행되면 로그를 연다. 진행 표시가 나온다.
5. 끝나면 결과가 그 브랜치에 커밋된다 → `docs/backtest_us.md`

> **브랜치를 반드시 바꿀 것.** `main` 으로 두면 백테스트 코드가 없어 그냥 건너뛰고 끝난다
> (실패가 아니라 "건너뜀" 이라 성공처럼 보인다).

**워크플로가 목록에 안 보이면** — `workflow_dispatch` 는 워크플로 파일이 기본 브랜치에
있어야 Actions 탭에 나타난다. 이미 올려두었으므로 보여야 한다.

## B. Google Colab

`backtest/colab.ipynb` 를 Colab 에서 연다.

- GitHub 에서 파일을 열고 **Open in Colab**, 또는
- Colab → 파일 → 노트북 열기 → GitHub 탭 → `milianjw8-hue/jwcha-stock` → `backtest/colab.ipynb`

셀을 위에서부터 순서대로 실행한다. 0번(드라이브 캐시)을 켜두면 세션이 끊겨도
받아둔 시세가 남아 재실행이 훨씬 빠르다.

비공개 저장소면 1번 셀의 `TOKEN` 에 GitHub Personal Access Token(repo 읽기)을 넣거나,
브랜치 ZIP 을 받아 `/content` 에 업로드한다.

## C. 로컬 PC

```bash
git clone -b main https://github.com/milianjw8-hue/jwcha-stock.git
cd jwcha-stock

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

```

Python 3.10 이상. 결과는 `docs/backtest_us.md`.

## 1. 실행 전략 — 순서를 지킨다

```
① quick (2~5분)      파이프라인이 도는지만 확인. 숫자는 보지 않는다.
        ↓ 통과
② 미장 --no-sweep    스윕이 가장 오래 걸린다. 먼저 성과부터 본다.
        ↓ 결과 확인
③ 미장 전체          스윕 포함. 파라미터 비교표를 얻는다.
        ↓
④ 국장               가장 느리다. 미장에서 배운 걸 적용한 뒤 돌린다.
```

**①을 건너뛰지 않는다.** 두 시간 돌리고 마지막 단계에서 죽는 것이 가장 아깝다.

### 중단되면

받아둔 시세는 `backtest/cache/` 에 종목별로 남는다. 그냥 **같은 명령을 다시 실행**하면
이미 받은 종목은 건너뛴다. 국장 유니버스(분기별 스냅샷)도 캐시된다.

캐시를 지우고 처음부터 받으려면 `rm -rf backtest/cache`.

## 2. 결과 읽는 순서

리포트를 위에서부터 읽지 말고 **이 순서로** 본다.

### 1순위 — 3절 "무엇이 신호를 탈락시키는가"

```
| core 항목 | 탈락 | 비율 |
| us_b2     | 1589 | 99.7% |   ← 이 하나가 룰셋 전체를 막고 있다
```

탈락률 90% 이상인 항목이 있으면 **다른 숫자를 볼 필요가 없다.** 규칙이 진입을
거의 못 하게 막고 있다는 뜻이고, 그 상태의 기대값은 표본이 없어 무의미하다.

→ 조치: 해당 항목의 `core: true` 를 빼거나, 판정 문턱(`verdict.go`)을 낮춘다.
   `docs/rules/us_minervini.json` 수정 후 재실행.

"자동 판정 불가 — 백테스트에서 항상 탈락" 표시가 붙은 항목은 **규칙이 나쁜 게 아니라
측정이 불가능한 것**이다(국장 수급 지표 등). 이건 고치지 말고 그대로 둔다.

### 2순위 — 2절 "기준선 대비"

```
→ 기준선 +0.102R vs 룰셋 +0.310R — 룰셋이 기준선을 개선했다
```

기준선은 "52주 고점 근접 + 거래량 증가"만 보고 전부 산 결과다.
**룰셋이 이걸 못 넘으면 26개 체크리스트가 아무 일도 안 하고 있는 것**이다.
그럴 땐 항목을 늘리지 말고 줄인다.

### 3순위 — 1절 "현행 룰셋 성과"의 기대값

- **기대값 ≤ 0** → 이 규칙으로는 매매하지 않는 편이 낫다. 규칙 재설계.
- **0 < 기대값 < 0.2R** → 수수료·슬리피지를 먹으면 사라질 수 있다. 얇다.
- **기대값 ≥ 0.3R** → 쓸 만하다. 다만 표본 수(n)가 30 미만이면 아직 판단하지 않는다.

함께 볼 것: **최대 연속 손실**. 이게 8회면 실전에서 8번 연속 잃는 구간을 견뎌야 한다.
견딜 수 없다면 기대값이 좋아도 그 규칙은 나에게 맞지 않는다.

### 4순위 — 6절 "과최적화 검증"

```
→ 유지율 41% — 과최적화. 이 가중치를 앱에 반영하면 안 된다.
```

학습기간(2019~2023)에서 뽑은 가중치를 검증기간(2024~)에 그대로 적용한 결과다.
**60% 미만이면 그 가중치는 과거에만 맞는 숫자**다. 반영하지 않는다.

### 5순위 — 4·5절 항목별 lift 와 제안 가중치

`유의 ✅` 가 붙은 항목만 의미가 있다. `|t| < 2` 는 우연과 구분되지 않는다.
유의한 항목이 2~3개뿐이라면, **그 2~3개만 남기고 나머지를 버리는 것**이
가중치를 조정하는 것보다 낫다.

### 6순위 — 7절 파라미터 스윕

최고값을 그대로 고르지 않는다. 그 자체가 과최적화다.
성과가 **평평한 구간의 중앙값**을 고른다.

```
stop_pct=3: 0.154R    ← 최고지만 옆 값과 차이가 크면 불안정
stop_pct=5: 0.102R
stop_pct=7: 0.081R
stop_pct=8: 0.063R
```
단조 감소면 3이 진짜 좋은 것일 수 있다. 들쭉날쭉하면 노이즈다.

## 3. 반복 사이클

```
백테스트 실행
    ↓
3절에서 병목 항목 확인
    ↓
docs/rules/*.json 수정   ← core 해제 / 문턱 조정 / 항목 삭제
    ↓
재실행 (캐시가 있어 훨씬 빠르다)
    ↓
2절에서 기준선을 넘었는지 확인
    ↓ 넘었으면
6절 유지율 60% 이상인지 확인
    ↓ 통과하면
제안 가중치를 docs/rules/*.json 에 반영 → 앱·스캐너에 자동 적용
```

**규칙 수정은 한 번에 하나씩** 한다. 두 개를 동시에 바꾸면 어느 쪽이 효과를 냈는지
알 수 없다. 매 사이클마다 무엇을 바꿨고 기대값이 어떻게 변했는지 적어둔다.

수정을 반복하다 보면 그 자체가 과최적화가 된다. **사이클 5회 정도가 한계**라고 보고,
그 안에 기준선을 못 넘으면 규칙을 늘리지 말고 근본적으로 단순화한다.

## 5. 이 백테스트가 말해주지 않는 것

정직하게 적어둔다. 리포트 숫자를 실전 수익률로 읽으면 안 된다.

- **수수료·세금·슬리피지 미반영.** 실제 성과는 이보다 낮다. 국장 거래세만 해도
  왕복 0.2% 이상이고, 이는 기대값 0.05R 정도를 갉아먹는다.
- **미장 생존편향.** 현재 지수 구성종목만 쓰므로 그동안 퇴출된 종목이 빠져 있다.
  실제보다 좋게 나온다. 국장은 시점별 종목 목록을 써서 이 편향이 없다.
- **국장 수급 지표 미반영.** 거래대금 상위 유지일수·연속 순매수는 과거 재현 비용이
  커서 판정 불가로 뒀다. 국장 결과는 보수적으로 읽어야 한다.
- **체결 가정.** 시가 체결을 가정한다. 유동성이 얇은 종목에서는 낙관적이다.
- **수동 항목 미반영.** "테마 대장주 여부", "명확한 촉매" 같은 사람 판단 항목은
  백테스트가 판정할 수 없다. 실전에서 이 항목들이 성과를 좌우한다면, 백테스트
  결과와 실전 결과가 갈릴 수 있다.

그래서 백테스트의 용도는 **"이 규칙으로 돈을 번다"의 증명이 아니라 "이 규칙은
확실히 아니다"의 반증**이다. 기대값이 음수면 확실히 버려야 하고, 양수라고 해서
확실히 좋은 것은 아니다.
